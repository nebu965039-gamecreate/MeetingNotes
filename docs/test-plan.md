# 総合テスト計画 — 商談メモ

次のクローズドテスト配信（`docs/release-notes.md` の「7回目」）に向けた回帰テストの一覧。
実装済み機能を横断的に洗い出し、**誰が確認できるか**（実機を持つ人 / Claude が担当できるか）を
項目ごとに分けている。「実装後は検証のみ行う」方針（ビルド・テスト・lintの自動確認＋定型5項目報告）を
補うためのチェックリストで、機能テストそのものを毎回全部やる必要はない。**★は今回のセッションで
変更が入った箇所（重点確認）**。

## 凡例

| タグ | 意味 |
|---|---|
| 🤖 AI可 | Claude がエミュレータ + `adb` 操作、または JVM/インストルメンテーションテストで確認できる |
| 📱 実機必須 | 実機のハードウェア・実際のGoogleサービス・実際の音声が絡み、エミュレータや自動テストでは代替できない |
| 🤝 分担 | Claude がエミュレータで一次確認し、実機で最終確認するのが望ましい（どちらか一方でも実施可） |

**AI（Claude）にできないこと**の前提: エミュレータは日本語の音声入力に対応していない（`SpeechRecognizer` の
オンデバイス日本語モデルが無い）、実際のGoogle Playの購入導線・広告配信網・プッシュ通知の実挙動、
実機の触感（誤タップのしやすさ・スライド操作の感触）は確認できない。逆に、画面遷移・レイアウト崩れ・
DBの整合性・エクスポートファイルの中身・ダークテーマ切替などはエミュレータと `adb` で確認可能（CLAUDE.md
の「adb操作の既知の落とし穴」参照）。

## 0. 自動化済み（ビルドのたびに実行、🤖 AI可）

```bash
./gradlew.bat testDebugUnitTest          # JVMユニットテスト(20ファイル、下記)
./gradlew.bat lintDebug                  # 静的解析
./gradlew.bat assembleDebug               # ビルド確認
./gradlew.bat connectedDebugAndroidTest  # インストルメンテーションテスト(エミュレータ必須)
```

JVMユニットテストが対象にしている純粋関数/ロジック（実機確認は不要、ロジック変更時のみ意識すればよい）:

| テストファイル | 対象 |
|---|---|
| `ClientDealPhaseRulesTest` | ★案件フェーズの代表値算出(進行中の最先端/成約/失注/0件) |
| `FollowupRulesTest` | ToDoボードの抽出条件、★表示フェーズが案件フェーズ由来になっているか |
| `StaleDealRulesTest` | 「動いていない案件」の21日判定 |
| `SalesRulesTest` / `AnalyticsRulesTest` | 売上・活動・顧客・フォロー集計 |
| `MeetingArchiveSearchTest` | 検索・並び替え |
| `TodoDueDateTest` / `TemplateVarsTest` / `JapaneseHolidaysTest` | 期限解決・テンプレ差し込み・祝日判定 |
| `ClientCsvTest` | CSV入出力のパース |
| `CreditPolicyTest` | 無料枠クレジットの月次リセット |
| `MigrationIntegrityTest` | Migration の抜け漏れ検出(v5→現行まで1段ずつ揃っているか) |
| `AnthropicClientTest` / `TranscriptPreprocessorTest` | 要約リクエスト整形・前処理 |
| `PdfExporterTest` / `WordExporterTest` / `ExcelExporterTest` / `CsvExporterTest` / `IcsExporterTest` / `MarkdownExporterTest` / `MeetingExportContentBuilderTest` | 各エクスポート形式の生成内容 |

インストルメンテーションテスト（実機/エミュレータ必須、🤖 AI可＝エミュレータで実行できる）:
`MigrationTest`（DB v5→現行の実SQL）、`MeetingDatabaseTest`、`FolderDaoTest`、`ClientGroupDaoTest`、
`UserCreditsDaoTest`。

## 1. ★フェーズ体系の一本化（今回の目玉、重点確認）

| 項目 | 確認内容 | 区分 |
|---|---|---|
| 案件0件のクライアントで初回商談を保存 | 保存直後に「案件を登録しますか？」ダイアログが出る。案件名+フェーズ(AI推定が既定)を入力して作成できる／「あとで」でスキップできる | 🤖 AI可 |
| 進行中案件が1件あるクライアントで商談を保存 | AI推定フェーズと現在の案件フェーズが違う場合のみ「案件フェーズを更新しますか？現在→AI推定」が出る。一致する場合は何も出ない | 🤖 AI可 |
| 進行中案件が2件以上あるクライアントで商談を保存 | プロンプトが出ない（対象外の仕様どおりか）ことを確認 | 🤖 AI可 |
| プロンプトで「更新する」/「あとで」を選ぶ | 選択後にクライアント詳細画面へ正しく遷移する。案件フェーズが実際に更新される（クライアント詳細の情報タブ・アーカイブの案件表示で確認） | 🤖 AI可 |
| 既存データの自動バックフィル | 旧データ（商談はあるが案件が0件のクライアント）を持つ状態でアプリを更新起動 → 自動で「案件」が1件作成され、フェーズが最新商談の実効フェーズになっている（`app_migrations`の`client_projects_backfilled`が2回目以降は走らない） | 🤖 AI可(sqlite3で事前状態を作って検証) |
| ホームのドーナツ・成約率 | 案件フェーズを直接変更（クライアント詳細⋮「プロジェクトを管理」）した後、ホームのドーナツ・全期間の成約率・成約数/失注数に**即座に反映**される | 🤖 AI可 |
| 商談詳細のフェーズ変更 | 商談詳細でフェーズタグを手動変更しても、ホームのドーナツやクライアントの「現在のステータス」は変わらない（商談フェーズ＝スナップショットである確認） | 🤖 AI可 |
| パイプラインボードが完全に消えていること | どの画面からもパイプラインへの導線が無い、`Routes.PIPELINE` 遷移が発生しない | 🤖 AI可(コードレビュー済み・画面上も確認) |

## 10. AIが担当できる範囲の補足

- **画面遷移・レイアウト・DB整合性・ファイル出力**は Claude がエミュレータ(`adb shell input tap` / `uiautomator dump` で座標を特定)や `sqlite3` での直接検証、JVM/インストルメンテーションテストで確認できる。CLAUDE.md の「adb操作の既知の落とし穴」を参照。
- **色・コントラスト・「見やすいかどうか」の最終判断**はスクリーンショット越しの確認になるため、実機の実際の画面での見え方(輝度・視野角・実機ごとの発色差)は人の目での確認を推奨する（🤝 分担に分類した項目）。
- **音声・実際の通知・実際の決済・実際の広告配信**は、Android のセキュリティ機構やGoogleサービスとの実連携が必要なため、エミュレータ/自動テストでは代替できない（📱 実機必須に分類した項目）。
- 依頼のしかたの例: 「①②③(セクション番号)をエミュレータで確認して」と言えば、Claude がその場でエミュレータを起動し `adb` で操作・スクリーンショットを撮って結果を報告できる。実機でしかできない項目は、確認後に気づいたことを伝えてもらえれば追跡・修正する。
